# Changelog

## 0.1.0 — 2026-10-31 — first public release

- Pipeline from request to reviewed pull request: intake, PRD, research, planning, implementation, verification, PR gate, review and QA.
- Independent verification before any pull request exists, with bounded fix rounds for small, actionable problems and escalation to human review otherwise.
- Evidence contract: every change records its base and head commits, changed files and each check's result; only fully verified work passes the automated gate.
- Per-repository verification policy, fail closed by default, with an explicit per-product opt-in for work without executable checks.
- Transactional outbox and idempotent consumers across all services.
- Planner with acceptance criteria, evidence-backed file claims, automatic normalisation of common plan defects and a recorded-decomposition regression corpus.
- Implementation loop with pinned base commits, per-edit syntax checks, stuck detection, bounded repair and a pre-commit test gate.
- Research with a code knowledge graph, vector search, request-named seed files and loop protection.
- Per-work-item token and time budgets with compact prompts for local models.
- Config snapshots, shadow evaluation and rollout gates for prompt and model changes.
- Operator dashboard, chat, customer portal, Jira and GitHub integration.
- Sealed benchmark corpus of 40 real upstream tasks in Go and TypeScript.
- Codex versions are numbered per product and branch, record typed changes (`module:<name>`, `section:<key>`, `patterns`, `anti_patterns`) and announce themselves on the `codex.indexed` topic. Incremental indexing writes product-scoped module rows and a version when a module changed. Each work item records the codex it was planned against (`work_item_codex_pins`).
- No planning or implementation on an empty codex. `product-agent`, `research-coordinator` and `implementation-planner` share one grounding gate (at least one codex module on the item's branch, with the product's default branch as fallback); a refused item is blocked with a Re-index / Retry / Cancel escalation and re-runs where it stopped once a re-index grounds the codex (`CODEX_REINDEX_TIMEOUT`, default 2h, re-escalates a re-index that never reports back). Empty codex lookups (`codex.gap`) are counted per run; more than `CODEX_GAP_THRESHOLD` (default 5) flags the evidence `ungrounded`, which never releases or approves automatically.
- In-flight work is re-planned when the codex changes. `status-orchestrator` consumes `codex.indexed`, waits for a quiet window (`CODEX_REPLAN_DEBOUNCE`, default 10m, kept in Postgres), and sends parents in planning or implementation whose pinned modules changed (or any pinned parent when `autonomous_scope`, `review_triggers`, `risk_zones` or `zones` changed) back to planning: in-progress subtasks are blocked with `codex_changed`, and the planner plans again from the existing brief against the current codex. After `CODEX_REPLAN_MAX` (default 2) automatic re-plans, or with less than `CODEX_REPLAN_MIN_TOKENS` of the token budget left, the operator is asked instead (Re-plan / Continue as is / Cancel). Items in verification, review, human review or QA, or with an open PR or pending change, are not touched; the dashboard shows "codex changed since planning" on them. Work item cards show the pinned codex version and modules, and the activity timeline shows each re-plan with the modules that changed.
- Codex zones per repository with a policy (`autonomous`, `human_review`, `escalate`) and glob patterns (with `!` exclusions). Defaults come from the embedded `configs/codex-config.yaml`; onboarding proposes zones from the `risk_zones` answer; Admin → Products → Repository → Zones edits, freezes and thaws them. Every zone change writes a codex version (`section:zones`), which re-plans affected work. The planner gives tasks their zones and escalates instead of planning into a frozen zone; at finalize a `human_review` zone flags the evidence `zone_review_required` (always human review, whatever `HUMAN_REVIEW_REQUIRED` says) and an `escalate` zone blocks the subtask before verification; the PR body lists the zones touched.
- Optional Redis (`REDIS_URL`, empty = disabled) shares real-time state across replicas: the dashboard WebSocket fan-out and the portal and LLM router rate limits. Without it every service keeps its in-process behaviour; `dashboard-backend` refuses to start with `DASHBOARD_REPLICAS` > 1 and no Redis. Compose has a `redis` service under the `scale` profile; Helm has `redis.enabled` and `redis.url`.
- `change-reconciler` does not block in-flight work items after an external change; external changes reach in-flight work only through indexing and the re-plan above.
- GitHub webhooks must be signed. `webhook-listener` verifies `X-Hub-Signature-256` (HMAC-SHA256, constant-time comparison) on every delivery against the secret saved on the dashboard (Admin → Integrations → GitHub → Webhook Secret), falling back to `GITHUB_WEBHOOK_SECRET`; a secret saved or rotated on the dashboard applies without a restart. With no secret configured anywhere, every GitHub delivery is refused with 503 and a log line saying what to set; missing or wrong signatures are refused with 401.
- The Helm chart deploys the per-service images the release workflow publishes, `ghcr.io/autonomous-engine/ae-<service>`, tagged with the chart's release (`v0.1.0`) by default (`image.registry`, `image.repositoryPrefix`, `image.tag`; `stable` follows the newest release).
- Compose publishes the gateway (8082), webhook listener (8081) and dashboard API (8080) on 127.0.0.1 only, since they have no login of their own.

### Upgrade notes

- A fresh install needs nothing beyond the quick start: `status-orchestrator` applies every migration (001 to 063) on first start.
- Set a GitHub webhook secret (dashboard or `GITHUB_WEBHOOK_SECRET`) and enter the same value in each repository's webhook settings on GitHub; until then GitHub deliveries are refused.
- Running a pre-release build from `main`: stop all services, rebuild them together, and start them together; no older binary may keep running against the migrated database (for example, binaries built before migration 060 insert codex version rows without `product_version`, and those inserts fail). Rolling back a migration (its down migration, newest first) also requires rolling back every service to a build before it.
- Redis is opt-in: leave `REDIS_URL` empty for a single-replica install. To run more than one dashboard replica, start Redis (`docker compose --profile scale up -d redis`) and set `REDIS_URL`.
